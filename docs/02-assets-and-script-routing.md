# 02 · 资源文件、模板与真实加载路径

## 文件地图

|---|---|---|
| data01/*.gfs | 有索引的Reverge资源归档 | 当成普通ZIP，或直接全量覆盖 |

资源标识有大小写/上下文差异：加载选择中常见cow、uni、bscout；运行时数据名可见Uni、Velvet。应记录每一层实际值，不随意把所有名称转小写后匹配。

## GFS：先做只读索引

本次解析的Reverge Package File版本为1.1，索引采用大端数值：起始u32给出数据区偏移；若干u64长度前缀字符串和条目数；每条含路径、大小、对齐值。实际数据偏移要按每条alignment推进，不能把文件名后面紧跟的内容当文件体。

解析必须检查：版本、索引边界、安全整数、条目数/字符串长度上限、alignment非零、条目区间不越过文件、索引不覆盖数据。重打包时则保留路径、内容和对齐语义，并对未修改条目逐字节比对。

[只读索引示例](../examples/read_gfs_index.py)只读取目录信息，不提取、执行或修改条目。它是本构建样本格式的演示，不是全版本GFS通用库。严禁用它“修复”不认识的版本。

## TFHRES与缓存

本次resources_prod/lobbymaps_prod样本可读出SQLite schema，包含cached_textfile、cached_image、filemap_record等表。它们提供逻辑名、来源路径、缓存文本/图像等线索。先只读打开并检查schema，不直接改所有表。Velvet Beautifier的TFHResource管理逻辑展示了备份、克隆、Upsert再保存的流程（S2）。

缓存里出现某路径，不代表原始磁盘文件的修改会被直接加载；也可能仍命中已打包/缓存版本。不要把资源键、开发源路径和当前实际读取路径混为一谈。

## template、temp、Scripts：不能凭名字排优先级

`temp/`可能是包内序列化资源路径的一部分，不一定是可以清理的临时目录。`template`可能是真正被引用的模板，也可能只是开发样例；`*.template.lua`也可能是我们自己的生成源，实际装包的是生成后的Lua。

判断执行路径的流程：

1. 从当前菜单/XML/加载键出发，记录引用的精确逻辑路径。
2. 在本构建归档索引里找到对应条目，比较解包副本与条目哈希。
3. 查`require`、初始化回调和资源查找接口，但把静态引用先记作候选。
4. 先只读观察加载/调用；若确需修改，备份后加入唯一的轻量诊断标记，验证到达时机。
5. 还原标记，确认未改条目和当前安装哈希；避免多个包的同名副本同时变化。

我们没有证明“template目录永远才是正式脚本”，也没有完整还原所有资源搜索顺序。谁实际被加载，应由本次调用链证明。

## 怎样使用第三方工具而不夸大依赖

Velvet Beautifier给了资源格式、包修改/恢复、TFHRES与关卡安装的重要参考。后续小工具并不是简单打开它的“隐藏角色开关”：角色加载位置、生命周期、输入派生字段、Boss控制和预测隔离需要另外调查。

既不能把上游工作略去，也不能声称运行时发现都是上游已经提供的SDK。公开分享应链接具体来源和许可，不附带完整游戏归档。参见[SOURCES.md](../SOURCES.md)。

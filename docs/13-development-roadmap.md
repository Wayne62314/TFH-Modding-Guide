# 13 · 项目路线、失败的价值与下一步

## 我们实际上怎样积累出这些项目

| 阶段 | 问题 | 获得的可复用信息 | 产物/边界 |
|---|---|---|---|
| 资源盘点 | 脚本和隐藏角色在哪 | GFS索引、资源键、Lua/XML/INI及角色候选名 | 只读索引，不是完整FOIT反编译 |
| 选角修改 | 为什么确认后不对 | UI呈现/合法选择/真实加载分层 | 改格子并非最终方案 |
| 教程最小实验 | 熊能不能由玩家控制 | 原教程初始化与预加载、崩溃场景依赖 | 保留原流程后用户成功 |
| 普通模式接入 | 不想进特殊教程 | 原生加载调用、待加载名、P1限定、模式组合 | 训练/本地CPU/双人逐项验证 |
| 基础Boss | 增强标志是否足够 | Flag布局与角色外层重置时机 | 增强不是完整Boss |
| 三阶段/Fred | 谁控制本体、子对象、收尾 | 状态排队、位置同步、所有权、碰撞依赖、请求状态机 | 手动控制实验，不等于剧情全复刻 |
| 性能优化 | 能用却严重卡顿 | 原生查询代价、作用域缓存、少扫表/少日志 | 用户确认流畅，不保证所有机器 |
| 跨角色招式 | 有判定没动画/召唤一次就坏 | 状态名、图集、供体资源和对象退出不能混用 | 多项条件性成功/失败保留 |
| 防御/拆投 | 显示成功却真实没生效 | 接触与输入分离、普通投范围、预测分支污染 | 离线测试，边界仍有漏防 |
| 原生/键盘输入 | 方向/攻击如何真正执行 | 朝向转换、基础及派生字节、合法边沿、焦点/停止 | 指令栏不再是唯一证据 |
| 回放/真人数据 | 能否只靠录像学习 | 输入格式、同帧pre、独立对齐、分段、隐私 | 候选不是已认证专家数据 |
| 模型迭代 | 高匹配却不主动出招 | 保持基线、历史误差、相对坐标、闭环区别 | 模型弱点公开，不夸胜率 |
| 连段执行 | 不想手录所有素材 | 内置动作库、节点、命中后缀、时序与状态确认 | 首条内置路线用户验证成功 |

这些产物共享一个底座：读取资源形成假设，在已识别生命周期中只读观察，以最小修改验证，再把有效结果固化成有保护的适配器和测试。不是每个MOD都从零开发，也不是靠一个万能反编译器自动生成。

## 当前最值得复用的资产不是哪份ZIP

- 对资源层/显示层/玩法层的分层认识。
- 加载、重置、真实更新、输入和状态生命周期的已验证连接点。
- 清晰的角色、场景、代数、线程、模式约束。
- 能区分原始输入、最终输入、显示指令和实际动作的验证方法。
- 能识别预测/重复/未来信息污染的数据管线。
- 正常输入执行层与命名动作序列的分工。
- 失败记录和反证：预加载不能单独解释崩溃；同名不能解释表现；写位不能解释完整Boss。

## 尚缺的信息

完整FOIT执行/编译规格、资源搜索与缓存优先级全图、全角色状态/取消与帧窗口、原生AI序列选择和任意中间节点接入算法、通用独立资源预加载、可靠全Boss退出、所有模式/网络协议、强模型的独立测试和闭环指标。

不应通过扩大白名单或强制状态跳转来掩盖这些缺口。下一步可以并行研究，但每项仍从小问题开始。

## 给其他作者的最小新项目流程

1. 先选一个明确目标和一个角色/模式，不同时动素材、规则、UI和网络。
2. 固定构建、备份原资源；列出所需脚本/状态/对象，不先全包替换。
3. 只读记录正常流程与目标差异，使用同一个观测时机。
4. 最小实验只改变一项，设置显式停止与回退。
5. 同时验实际动作、输入、资源、帧时序、结束和重赛。
6. 失败时回原版做对照；不把无日志/无动画都当成同一种失败。
7. 有证据后才扩大范围，保留作用域约束及未知项。
8. 发公开文档/补丁，不把私人研究目录直接公开。

欢迎补充反例：请提供构建哈希、精简复现步骤和脱敏结果。不同构建不一致是有价值的信息，而不是必须绕过的障碍。

# 07 · 卡顿、预测分支和对象生命周期

[English](en/07-performance-and-prediction.md)

## 不要用“脚本很短”估计开销

三阶段普通对战接入后曾严重卡顿。调查发现一些底层辅助操作在真实游戏里比孤立微基准昂贵得多，例如频繁查询内存区域。每帧对多个对象查范围、扫描状态表、反复创建字符串/闭包或写完整日志，会乘上角色、子对象和预测更新的次数。

我们的优化方向是：把慢查询移出常规帧路径，缓存到“场景＋角色实例＋资源数据＋代数”作用域；只在变化/缓存未命中时做昂贵检查，常规路径只做边界比较。优化后用户确认卡顿消失，但这不构成所有机器的帧率保证。

## 缓存必须有明确失效条件

```text
进入新scene / actor / data / generation
    → 清空旧范围、状态表、名字及子对象缓存
当前作用域首次查询
    → 验证范围与身份，缓存有限条目
后续帧
    → 轻量边界检查；遇到重建、退出、错误即作废
```

内存区域可读/可写只说明映射仍在，不证明里面还是原对象。对象池槽位可被复用，父指针也可过期。寻找Fred应先得到活对象集合，再有界追父级确认归属；不能无限追一个任意指针。

状态表/字符串也有资源生命周期。永久缓存一次扫描出来的状态地址，换角色或重赛后继续用，是“起初成功后来随机崩”的典型来源。

## CPU会产生非真实更新

本次观察到AI预测相关递归及输入调用。一次外部更新里可能执行大量预测工作，它们会经过与真实战斗相似的状态/输入代码。若把每次Hook当一帧，就会出现：重复训练样本、预测结果污染、假拆投成功、重复召唤或时钟飞快。

隔离应覆盖两层：

- 根更新入口检查预测标志并维护预测深度，防止递归内部暂时清标志后漏进来。
- 每次输入/接触回调再次检查标志；某些预测输入可能没有经过一次新的根入口。

还要检查主scene、线程、更新参数、真实根深度、嵌套情况、入口/出口计数恰好推进1。未通过的记录是诊断，不伪造成中立动作或真实帧。

## 测量报告怎么写

区分：单个API微基准、整个Hook耗时、原生scene根调用墙钟、用户感知卡顿。根调用包含游戏自身工作及预测，不能把全部时间归咎于采集器；同时在独立测试进程测得快，也不证明在游戏中快。

至少记录样本量、场景、对象数量、缓存命中/失效次数、写盘量，以及用户反馈。计算p50/p95/p99时注明测的是什么。诊断日志分批、设体积/时长上限，错误后正常卸载并冲刷尾批。

## 不要每帧重启状态

召唤、漩涡、飞行等都应是有状态的请求：按键边沿→排队→确认进入→等待结束→恢复。每帧调用“开始召唤”会把进度拉回起点；每帧反复改标志/切状态也可能让角色锁在红色中间态。

停止控制器与撤销已经进入的原生效果不同。清理失败时应报告需重启，不能对已失效对象强行“恢复”。公开实现S1的作用域缓存、控制器和shutdown接口可作工程参考。

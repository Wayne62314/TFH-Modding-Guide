# 04 · 大熊：从选角失败到战斗加载替换

## 初始目标与失败

目标是玩家操控Huggles。文件调查发现内部候选名bscout，并在剧情Boss初始化中看到预加载及角色设置。最初尝试选角列表/Arizona替换：预览仍显示Arizona，确认后有时变成其他角色。这说明修改触及了流程，但不能证明有效角色已经进入战斗。

至少有三层需要区分：

- **选角呈现**：格子、头像、名字、预览动作。
- **选角合法性/提交**：确认时能否接受角色标识，是否被回退或另行选择。
- **战斗实例化**：实际加载哪份角色数据、调色板、状态和资源。

不能从“界面格子有限”直接推导必须改UI，更不能把随机回退断言为某个已确认的校验函数，除非追到了该分支。

## 为什么先走教程

教程已有可信的场景、目标、对话、角色初始化接口。把原移动课程保留，只在已有matchSettings回调增加最小熊设置，比重建整节自由测试场更能保留引擎依赖。

首轮自定义初始化崩溃；加入预加载、移除训练功能仍崩溃。于是继续缩小改动范围，保持原有流程，最终用户看到了可操作的熊。成功证明的是这个最小路径可用，不证明最初崩溃的全部因果已经重建。

## 怎样进普通训练/本地对战

教程成功后，另查正常选角后的原生加载。观察到场景携带P1/P2待加载名，在已验证调用位置把P1的cow改为bscout，再让原生流程继续加载。用游戏自身字符串赋值逻辑管理C++字符串，熊调色板限定为已知的0。

这条路线不替换Arizona的图集/FOIT文件，也不把普通训练跳转成教程。P2保留。预览可能仍是Arizona，因为它位于前一层；进场真实角色才是主要验收对象。

本地CPU和本地双人分别采样、再分别验证。普通训练还有mode=10且training标志为1的路径，最早规则只认0导致分享版“没替换”，随后依据日志修正。**白名单条件错误也会表现为功能完全没反应**，不应先怀疑资源损坏。

## 这个MOD用了哪些有效信息

| 信息 | 用途 |
|---|---|
| bscout资源/剧情引用 | 找到真实内部角色候选 |
| 原教程初始化回调 | 获得可运行的最小加载环境 |
| 崩溃Scene依赖 | 避免过度重建场景 |
| 待加载名和已验证调用方 | 在普通模式精准改P1 |
| std::string赋值及函数字节 | 不破坏字符串生命周期，拒绝错版本 |
| 模式/训练组合 | 只在已验证离线流程应用 |
| 真实游玩结果 | 验证走跳、攻击与进入场地，而不是仅回读字符串 |

## 推广范围

用户已实测普通自由训练、本地CPU和本地双人可以变熊。隐藏敌人未必具备所有正式角色的胜利、重赛、配色或UI资产，后续仍需分别测试。关闭工具不会把现有熊实例立即还原，清除状态需重新加载，必要时完整重启。

源码位置见S1的加载钩子。先读本章过程再看RVA，才知道这个地址为什么被使用，以及什么时候不该使用。

# 03 · 从Lua接口定位原生行为

## 最小调查顺序

先提出可证伪问题，例如“P1的待加载角色名在哪个阶段被读取”，而不是先搜一堆地址改值。建议顺序：

1. 收集版本哈希、包索引、角色/状态名和脚本调用。
2. 在正常流程做只读观察，记录模式、调用方RVA、对象类型和进入/退出时机。
3. 比较正常角色与目标角色、普通训练与本地CPU的差异。
4. 找到能包住所需操作的最小生命周期点。
5. 再做单变量运行时实验，加版本/函数签名/上下文校验。
6. 用户确认动作、资源、输入、收尾；不要只看write回读或一条日志。

## 磁盘代码未必等于当前有效代码

本次一些目标位置的磁盘字节不能直接作为正常运行中的有效指令分析。采用只读ReadProcessMemory读取已加载模块，在确认构建哈希后反汇编。不能由这个现象泛化为所有位置、所有构建，也不需要发布完整代码段转储。

PE异常目录可辅助定位非叶函数边界；没有边界记录时只做小范围、有界的读取。字符串交叉引用、Lua绑定包装、RTTI/vtable和现有调用点相互印证，比单独相信反编译出的变量名可靠。

区分VA与RVA：日志/文档保存相对模块的RVA，运行时使用已加载基址加RVA。ASLR下不能把上一次绝对地址复制到下一次运行。RVA仍只对指定构建成立。

## C++字符串不是随便一块UTF-8

本构建若干字符串呈现MSVC小字符串布局：长度在+16、容量在+24；容量小于16时内容内联，否则对象首字段指向堆内存。读取前检查长度、容量和边界。写入时优先沿已确认的原生字符串赋值路径，不把新C字符串指针直接塞进复杂对象。

这里的布局是通过具体对象和包装函数验证的，不是所有std::string实现的通用承诺。内存可写也不代表分配器、所有权、终止符和销毁协议正确。

## 只读观察与修改的边界

Frida的Interceptor可观察参数/返回及上下文；NativeFunction可调用已定位的本机函数（接口说明见S3）。安装观察钩子本身仍是动态插桩，不要宣传成“完全没有注入”。我们说“只读采集”，是指不替换输入、不写玩法状态、不调用修改性游戏函数。

真正修改时，必须明确是哪一种：加载字符串替换、Boss标志、原生状态排队、输入私有副本。它们的停止和回滚不一样。不要在陌生线程、预测更新或对象初始化一半时直接调用游戏方法。

## 崩溃怎样变成有效信息

一次隐藏角色教程崩溃出现访问异常：Scene中的一个子指针为空，随后被按+0x60解引用。它能证明“场景内部依赖缺失/失效”，但不能仅据此把子对象叫作纹理或角色资源。早期加预加载仍崩溃，正好反证“必然只缺预加载”的结论。

后续保留原教程初始化，只追加最小角色设置，才把变量收窄。教训是：空指针位置、日志末句、Lua提示是否出现，都需要结合上下文；栈内地址扫描不是可靠展开后的调用栈，Lua pcall也挡不住原生访问异常。

## 正确的护栏组合

EXE哈希→函数字节签名→场景模式→调用方/线程→角色槽位与队伍→对象代数/数据身份→长度和范围→阶段→单次/限时→回读及观测。不能只选其中一项就称为安全。

一个可读可写的旧指针是最容易误判的对象。身份至少绑定scene、actor、data、generation及角色侧；换场、重赛、资源重建就作废。生命周期缓存见[07章](07-performance-and-prediction.md)。

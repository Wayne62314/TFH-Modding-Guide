# 06 · 防御与输入：四种方法不要混为一谈

[English](en/06-input-and-defense.md)

| 方法 | 改动位置 | 本项目经验 |
|---|---|---|
| 接触结果/标志辅助 | 命中判定附近的临时标志和结果 | 可做到某些即时防御，不等于真实方向输入 |
| 游戏原生输入副本 | 角色输入处理调用的私有输入结构 | 指令栏与实际动作可同时出现，适合连段/AI |
| Windows SendInput | 操作系统键盘事件 | 依赖焦点、键位和调度，更容易来不及 |
| 状态强制/排队 | 角色状态系统 | Boss控制实验用，不等于正常输入，也不应用来伪装连段成功 |

## 基础输入编码

本构建输入结构的主要观察为：偏移0是方向；偏移3/4/5/6分别为ABCD。原始按钮状态0=新按下、1=松开、3=按住、4=未按。内部ML类别索引可能另用0/1/2/3，转换时必须注明。

已逐项验证的屏幕方向包括0右、1右下、2下、3左下、4左、8中立。反射映射为`[4,3,2,1,0,7,6,5,8]`；上方斜向在执行路线中使用，但不是每个方向都经历同样独立校准。面向与屏幕位置不是同一个概念，输入时读取实际facing，而不是永远按A。

## 最关键的坑：显示A但没有攻击

只改ABCD基础字节时，指令栏出现A但奥莉没动作。通过“手动A→人工触发单次A”的同场对照，发现缺少派生字段。后续B/C/D与B+C采样校准后，实际攻击通过用户验证。

本构建校准映射：A=[3,19,25]、B=[4,20,26]、C=[5,18,24]、D=[6,17,23]。此外9..14是聚合通道：按指定按钮集合统计press/release/held数量，再按阈值生成。原生规则有优先级，不能把“任意按钮按住”简单OR成所有聚合值。

这张映射来自本构建的正常手动输入和原生聚合实现，不是键盘按键码，也不保证其他构建适用。[合成输入示例](../examples/input_edges.py)只演示合法边沿，不能单独拿来注入游戏。

## 私有输入副本原则

在已验证的调用点复制完整已知输入范围，只改变我们控制的方向/按钮及派生通道，再替换这次调用使用的指针。不要直接修改共享原始缓冲区；保留无关标志和不理解的字段。私有内存生命周期必须覆盖实际使用时间，不能把短命局部对象交给异步消费。

每次真实更新最多推进一次调度；同一计数下重复输入调用应看到相同边沿，不能第一遍press、第二遍就变held。路线拼接要根据实际已按住的按钮重新生成合法边沿，不能直接把录制中途的held粘进去。

## 防御与拆投的经验

早期即时防御辅助在已识别接触点临时使用Flag25并转入原生防御结果，保留正常削血。这种做法并不说明方向输入栏会显示拉后，也不是一套学习AI。

普通投的自动拆投则转为在真实输入入口发送B+C，让原生规则决定能否拆。范围只包括已识别普通前/后投和空投，不强拆指令投，也不随意扩大到受击或无法防御状态。CPU预测曾让日志显示成功、真实对局却没拆开，因此真实状态确认和预测隔离必不可少。

空防也不能仅检查y>地面：起跳、二段跳转换、接近落地等状态有各自规则。本项目仍有部分边界漏防，不能笼统声称全角色全状态100%成功。

## 为什么模拟键盘慢

观察、Python/JS通信、系统事件排队、焦点和游戏采样共同产生延迟。到命中接触时才通过SendInput拉后，常常来不及；要在已分类的起手或弹体到达前提前决策。错误模式规则还曾让整个系统直接跳过，现象同样是“太慢/没防住”。先看日志有没有实际提交输入，再调整时机。

原生输入也不自动解决“预测何时防、上下段怎么选、何时可防”的问题；它只是更直接的执行层。游戏内CPU的前向模拟不等于我们已得到可复用的通用防御决策接口。

## 公开使用边界

这些机制只在授权离线实验中讨论。本文不发布私密辅助工具、在线去限制版本或反作弊绕过方案。高频写入、输入抢占和遗漏松键都可能破坏正常操作；人工输入、失焦、暂停、模式改变和F10应使实验停止，不能为了成功率取消这些保护。
